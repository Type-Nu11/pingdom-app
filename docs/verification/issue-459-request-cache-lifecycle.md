# #459 요청 취소와 React Query 캐시 수명 검증

- 기준: `origin/dev`의 `93d52c2f`. 구현 위치: V2 및 보호 화면에 V2 QueryClient를 연결하는 application 조립 경계. V1 의존성 증감: **none**.
- Backend·Proxy·API 계약 변경 없음. #453의 검색 화면 분리와 #455의 커뮤니티 훅 구조 변경은 수행하지 않았다.

| 시나리오 | 변경 전 | 변경 후 |
| --- | --- | --- |
| 카페 검색이 지연된 상태에서 식당 검색 제출 | 새 검색이 막혀 제출 2번 중 1번만 실행됐다. 검색어 편집으로 화면의 결과를 비워도 기존 카카오 요청은 진행됐다. | 제출 2번 모두 실행되고, 이전 키워드·주소 요청 2개를 취소한다. 취소된 요청의 중심 좌표 없는 재검색은 0번이다. 새 검색의 동일 검색어 중복 제출은 막는다. |
| 검색 화면 이탈 | 이전 카카오 요청의 타이머가 최대 8초까지 남을 수 있었다. | 활성 요청 2개 모두 취소되고 늦은 응답을 무시한다. 타이머와 호출자 리스너는 응답 본문 처리까지 유지하고 성공·실패·취소 시 해제한다. |
| PUT 네트워크 실패 뒤 재시도 인증 중 취소 | Axios 1번 뒤 fetch 1번이 실제로 호출됐고 테스트에서는 성공까지 반환됐다. | Axios 1번, fetch 0번이며 `ERR_CANCELED`를 반환한다. fetch가 이미 시작됐다면 응답 본문 읽기 중에도 취소가 전달된다. 취소 에러는 React Query에서 재시도하지 않는다. |
| 로그아웃 후 다른 계정 로그인 | 보호 화면에서 같은 QueryClient를 재사용했다. 캐시를 비우더라도 이미 시작한 좋아요 같은 mutation 콜백은 이전 client에 결과를 쓸 수 있었다. | 이전 보호 화면 종료 시 조회를 취소하고 캐시를 정리한다. 다음 로그인은 비어 있는 별도 client로 시작하며, 이전 조회와 mutation이 나중에 완료돼도 다음 계정의 동일 query key에는 새 계정 데이터만 남는다. |

기준 사본에 동일 회귀 테스트를 적용해 검색 제출, 보호 화면의 QueryClient 재사용, 취소된 PUT 재시도를 재현했다. 위 요청 횟수와 캐시 결과는 제어한 응답으로 확인한 값이다. 실기기 네트워크·메모리는 측정하지 않았다.

## 유지한 동작과 근거

- 서버 장소 자동완성은 검색어·좌표를 query key에 포함하고 활성 검색어가 있을 때만 요청한다. React Query 신호는 API transport까지 전달된다. 자동완성 staleTime 30초, 지도 viewport 15초와 이동 중 기존 마커 표시를 유지한다.
- 커뮤니티 목록은 카테고리·국가·페이지 크기별로 키를 구분한다. 실제 InfiniteQueryObserver로 필터 교체 시 이전 요청 취소, 새 필터의 1페이지 요청, 구독 해제 시 취소와 늦은 페이지 미저장을 확인했다.
- 기본 staleTime은 30초, 비활성 gcTime은 5분이다. 커뮤니티 시트는 페이지당 20개를 요청하며 서버의 다음 페이지 여부를 따른다. 활성 화면에서 페이지를 잘라내면 이전 스크롤 목록이 사라질 수 있어 `maxPages`를 추가하지 않았다. 캐시 용량과 재조회 비용의 기준을 바꿀 실사용 측정값은 없다.
- 음성 API는 세션·호출자 신호를 전달하고 응답 크기 제한과 취소를 구분한다. 종료·다시 열기 테스트에서 늦은 이전 응답이 새 대화를 탐색시키지 않는 것을 확인했다.
- 계정 전환 확인 범위는 현재 앱의 로그아웃 후 재로그인이다. 이미 서버에 제출된 변경 요청의 롤백은 다루지 않는다. 이전 계정의 지연 mutation 콜백은 화면과 분리된 이전 client에만 접근한다.
